# 記事の構成と編集方針

## 伝えたいこと

TypeSpec を API 契約の正本にし、生成した OpenAPI を openapi_first に読み込ませると、Rails の実装と契約のずれを機械的に検証できる。
仕様の変更が検証条件にも反映されるため、AI エージェントへ実装を任せるときも、契約への適合を同じ基準で確認しながら開発を進められる。
読後に「Rails でこの開発体験を試したい」と思ってもらう。

読者は Rails と request spec を知っており、API First または AI エージェントによる開発に関心がある人を想定する。
TypeSpec と openapi_first の予備知識は要求しない。

## 構成

| 位置 | 読者に渡す内容 | 役割 |
| --- | --- | --- |
| 導入 | 仕様の変更が次のテスト実行から判定基準になる体験 | 導入時点で何が良かったのかを具体化する |
| 仕様とテストの関係 | 同じ解釈から作った実装と期待値が、仕様との差を見落とす問題 | 機械的な照合を導入する理由を示す |
| TypeSpec と OpenAPI | 共有する契約の図、型の再利用、HTTP の定義 | 仕様の正本と検証までのつながりを説明する |
| 必須項目の追加 | completed の仕様追加、既存テストの失敗、実装修正後の成功 | 開発体験の山場を実際の記録で裏付ける |
| openapi_first と Rails | 実行時の入力検証、RSpec のレスポンス検証 | 観察した失敗と成功が起きる仕組みを説明する |
| AI エージェントとの開発 | 合意した契約、実装依頼、同じチェックからのフィードバック | 記事の体験を日常の開発へ接続する |
| 検証範囲 | boolean の意味、未実行経路、意図せぬ仕様変更 | 品質のどの部分を支え、何に判断が残るかを示す |
| サンプルへの案内 | Swagger UI と README の演習 | 同じ失敗と成功を読者に再現してもらう |

本文は [article.md](article.md) に保存する。
製品比較や Rails アプリの全構築手順は広げず、TypeSpec と openapi_first の組み合わせによる体験を説明する。
サンプルの起動と作業コピーの作成は README に集約する。

## 主張の根拠

- TypeSpec の文法と OpenAPI 生成は公式ドキュメントを参照し、コード例はサンプルの実ファイルから抜粋する。
- openapi_first の機能は公式 README とサンプルの設定を照合する。
- completed 演習の失敗と成功は `docs/verification.md` および実行ログを根拠とする。
- AI エージェントとの相性の評価は、共通の判定基準を使う構成から述べる。生産性の数値や実証していない改善実績は付け加えない。
- 型の契約、業務動作、テストで実行した範囲を区別する。契約に適合したことだけで全体の品質を保証するとは書かない。

## サンプルの位置づけ

既存の completed 演習が記事の中心的な主張を実証しているため、アプリの機能は追加しない。
README の冒頭に記事へのリンクと演習への案内を加え、記事と実験の対応を明確にする。

## レビューと修正

初稿は技術面と文章面のサブエージェントが独立してレビューした。
公式ドキュメントのリンク切れを修正し、AI との相性の評価を構成からの推論として記述した。
全体図と仕様例の直後に中心の演習を移し、成功ログの直後に boolean 型と業務上の意味の違いを説明した。
検出できる不足を必須項目へ限定し、重複した評価も整理した。

修正版を別のサブエージェントが再レビューし、技術的な説明、主張の範囲、再検証結果、デモへの誘導に重要な残問題がないことを確認した。
再現結果は [検証記録](verification.md) に保存している。

## 公開時の確認事項

原稿とサンプルは現在のプライベートリポジトリに保存する。
本文のサンプルリンクは準備しておくが、一般公開する際は読者がリポジトリを閲覧できる公開範囲を決める必要がある。
この作業ではリポジトリの公開範囲や記事の公開先を変更しない。
